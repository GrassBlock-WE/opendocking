# OpenDocking architecture

This document describes how the OpenDocking (`odock`) source tree is organised,
what every Rust module is responsible for, how the crates depend on each other,
what happens during a docking run, how the work is parallelised, and how to
build and test the project.

It also contains the **step 1 deliverable** of the project brief: an explicit
directory-structure plan of the Rust workspace with a short comment on every
member and every source file (see [Directory plan](#directory-plan)).

Everything below is written from the source in this repository. Where a design
decision follows AutoDock Vina or AutoDock 4, the attribution is stated
explicitly.

---

The upstream AutoDock sources are **not** vendored: no file here is compiled
from, `include!`d from, or copied out of an upstream checkout. What the kernel
keeps is the numerical constants and the algorithmic structure of the published
implementations, each annotated at its definition site in `dock-core`; the full
attribution is in [`../README.md`](../README.md).

Pure Rust (`#![deny(unsafe_code)]`), no Python, no graphics, no `unsafe`.

### Why the viewport is not a `QOpenGLWidget`

The 3-D area was originally a `QOpenGLWidget` driving ModernGL on Qt's own
context. On the reference machine that produced a window whose 3-D area was
silently empty, and the cause is worth recording because it is invisible from
the outside:

* `paintGL` is called with Qt's framebuffer object bound, but **that framebuffer
  is not the one Qt composites**: clearing it to magenta never appeared on
  screen.
* Between frames Qt leaves its own GL state behind — measured with
  `glGetIntegerv`, `GL_COLOR_WRITEMASK` was `(1, 0, 0, 0)`. Because `glClear`
  *also* honours the colour mask, most of the clear and nearly all of the
  geometry were discarded.
* ModernGL caches GL state, so it skips a call it believes is already satisfied;
  it therefore cannot notice that the host changed the state behind its back.
  `ctx.detect_framebuffer()` and the `*_direct` capability calls exist for this,
  but they cannot fix the framebuffer/compositing mismatch.

`ViewportWidget` is consequently a plain `QWidget` that

1. owns a **standalone** ModernGL context (`moderngl.create_standalone_context`),
2. renders into **its own** framebuffer (colour texture + depth texture) at the
   widget's device resolution,
3. reads the pixels back and blits them with `QPainter`.

Nothing about the drawing depends on Qt's GL state, so the result is identical
on every platform and driver. It also makes the workbench testable without a
display: with `QT_QPA_PLATFORM=offscreen` the widget still renders, which is how
`tests/test_gui_viewport.py` guards against a regression.

### Workspace members, at a glance

| Member | Crate type | Purpose |
|---|---|---|
| `crates/dock-core` | `rlib` | The numerical kernel: typing, kinematics, scoring, search, grids, PDBQT I/O, orchestration. |
| `crates/dock-py` | `cdylib` + `rlib` | The `odock._odock` extension module; a thin typed wrapper around `dock-core`, with NumPy zero-copy in/out. |

`Cargo.toml` pins the workspace metadata once (`version = "0.1.0"`,
`edition = "2021"`, `rust-version = "1.75"`, `license = "GPL-3.0-or-later"`) and
every member inherits it with `version.workspace = true` and friends. The
release profile uses `opt-level = 3`, `lto = "thin"` and `codegen-units = 1`;
the dev profile deliberately disables debug info (`debug = 0`, `opt-level = 1`)
because the kernel's hot loops are numerically dense and the compiler's PDB
write is a needless bottleneck, while dependencies are still built at
`opt-level = 2`.

```text
        +------------+-------------+            +--------------+---------------+
                     |                                         |
     +---------------+----------------+                        |  PyO3 + NumPy
     |               |                |                        v

   (DVec3/DQuat/  (par_iter,      (DockError)       |  python/odock            |
    DMat3,        par_chunks)                       |  (import odock._odock)   |
    double prec.)                                   +------------+-------------+
                     |                                            |
                     |  optional, `--features gpu`                |  console script
     +---------------v----------------+                           v
     | wgpu 25 (wgsl, dx12, metal,    |                 +-----------------------+
     | vulkan) + bytemuck + pollster  |                 |  odock (CLI)          |
     +--------------------------------+                 |  odock.gui (optional) |
                                                        +-----------------------+
```

Rules that the graph encodes:

* `dock-core` never depends on `dock-py`, on Python or on any graphics crate in
  the default configuration. A plain `cargo build` needs nothing but a Rust
  toolchain.
* `dock-py` contains no numerics of its own; every entry point forwards to
  `dock-core` and converts types.
* The Python package imports the compiled module as `odock._odock`; nothing in
  `python/odock` talks to Rust in any other way.

## Data flow of a docking run

```text
   receptor.pdbqt            ligand.pdbqt
        |                         |
 (1)    v                         v
   parse_receptor_pdbqt      parse_ligand_pdbqt        io/pdbqt.rs
        |                         |
   ReceptorRecord            ParsedLigand { atoms, records, top, rotors, torsdof }
        |                         |
 (2)    |                         v
        |                    perceive_bonds + assign_types        molecule.rs
        |                         |   (geometric connectivity, X-Score types)
        |                         v
        |                    build_ligand_tree(top, coords, n)    kinematics.rs
        |                         |   (rigid clusters + torsion segments)
        |                         v
        |                    ligand_pairs(atoms, frame_ids, ...)  docking.rs
        |                         |   (intra pairs and macrocycle glue pairs)
        |                         v
        |                    num_tors(atoms, rotors)              scoring/mod.rs
        |                         |
 (3)    |                         v
        |                    MovableModel { atoms, coords, ligand, ligand_pairs,
        |                                    flex, flex_pairs, layout }
        |                         |   initial_conf() + apply()  -> forward kinematics
        |                         |
 (4)    v                         v
   NonCache::new(receptor, sf, dims)      scoring/noncache.rs   (exact scorer)
   AffinityGrid::populate(receptor, sf, types)  scoring/grid.rs  (search grid)
        |                         |
        +-----------+-------------+
                    v
 (5)             Shared { receptor, noncache, grid, sf, ligand_atoms, ... }
                    |   Arc<Shared>  (immutable)
                    v
                 System { shared: Arc<Shared>, movable: MovableModel, force_exact }
                    |
                    v
 (6)        Docking::run()  ->  run_search()  ->  parallel_monte_carlo()
                    |                              search/mod.rs
                    |   rayon over `exhaustiveness` independent starts
                    |   each: randomise -> mutate -> bfgs -> Metropolis
                    |         -> add_to_output_container
                    v
 (7)        refine_pose() per pose with force_exact = true     docking.rs
                    |   BFGS on the exact pairwise surface, Caps::authentic()
                    v
            System::score()  ->  ScoreComponents { total, inter, intra,
                    |                                 conf_independent, unbound }
                    |   affinity = total
                    v
 (8)        Docking::poses_pdbqt(energy_range)  ->  write_pose_pdbqt()
                    |                              io/pdbqt.rs
                    v
            multi-model PDBQT with a VINA-RESULT REMARK block per pose
```

Stage by stage, with the functions that do the work:

1. **Parse.** `parse_receptor_pdbqt` yields immobile atoms plus non-fatal
   `ParseIssue`s. `parse_ligand_pdbqt` parses the nested `ROOT` / `BRANCH a b` /
   `ENDBRANCH a b` language into a raw tree, then *flattens* it into a movable
   atom array, a `TopologyNode` tree and a `rotors` list. Atom names, residue
   information, partial charge and the AD4 atom type are read from the fixed
   PDBQT columns; the original line is kept as a template for output.
2. **Perceive.** `perceive_bonds` re-derives connectivity from the geometry
   (`d < 1.1 * (rcov_i + rcov_j)` plus the lens test that rejects a third atom
   lying between the pair), and `assign_types` re-derives every `XsType` from
   the element, the AD4 type and the bonding graph. `frame_ids` labels each
   movable atom with the rigid frame that owns it; `ligand_pairs` then builds
   the intra-ligand interaction list (different frames, at least four bonds
   apart) and diverts macrocycle closure pairs into their own `glue_pairs`
   list. `num_tors` computes Vina's effective torsion count from the `rotors`
   list.
3. **Build the kinematic tree.** `build_ligand_tree` walks the topology and
   produces one `Node` per torsion segment, each holding a half-open atom range
   and the axis/origin of its rotation. Every atom's coordinates are stored
   once in the tree-local frame (`KinematicTree::local`). `MovableModel` gathers
   the atoms, the coordinates, the tree, the pair lists and the `DofLayout`;
   `initial_conf` + `apply` round-trip the input structure through forward
   kinematics so the starting conformation is exactly the parsed one.
4. **Build the grid.** `GridBox::dims` rounds the requested box up to whole
   voxels; `NonCache::new` builds the exact scorer and its cell list;
   `AffinityGrid::populate` (or `gpu::populate_grid`, which falls back to it)
   fills one map per atom type the ligand actually presents, summing
   `pair_energy_xs` over every receptor atom within the cutoff. For AD4 the
   grid is skipped entirely (`is_grid_capable() == false`).
5. **Search.** `Docking::run` resolves the seed, derives the box corners,
   builds a template `System` and calls `run_search`, which dispatches to
   `parallel_monte_carlo` (default) or `island_lga`. Each independent start
   randomises the ligand inside the box, minimises with BFGS under the tight
   hunt caps, mutates one degree of freedom, minimises again, accepts with the
   Metropolis criterion at `T = 1.2`, and stores every accepted minimum in an
   RMSD-deduplicated container. The per-start containers are merged with a
   relaxed 2 Å dedup cutoff.
6. **Refine.** Every reported pose is re-minimised with `force_exact = true`, so
   the timings come from the grid but the reported energies come from the exact
   pairwise scorer. `refine_pose` runs BFGS under `Caps::authentic()` and
   re-scores the result.
7. **Score.** `System::evaluate` splits the energy into `inter` (grid or exact),
   `intra` (intra-ligand pairs plus glue pairs) and `unbound`, applies the
   force field's `conf_independent` rule and returns a `ScoreComponents`
   record. `ScoreComponents::total` is the reported affinity.
8. **Write poses.** The surviving poses are sorted by energy and truncated to
   `num_poses`; the RMSD of every pose to the best one is computed with
   `rmsd_lower_bound` / `rmsd_upper_bound`; `poses_pdbqt` renders each pose
   inside the energy window as one `MODEL` of a multi-model PDBQT document with
   a `VINA RESULT` remark block and the original `ROOT`/`BRANCH`/`TORSDOF`
   topology.

## Threading model

OpenDocking uses data parallelism only, through `rayon`. There is no shared
mutable state between threads and no locks in any hot loop.

```text
                    Arc<Shared>  ── immutable, ref-counted, shared by every task
                    │  receptor atoms, exact scorer, affinity grid, force field,
                    │  ligand templates, topology, pair lists, num_tors, dims
                    │
   System::fork()   │
   ┌────────────────┼────────────────┬─────────────────┐
   │                │                │                 │
   v                v                v                 v
 task 0           task 1           task 2     ...   task N-1      (N = exhaustiveness)
 MovableModel     MovableModel     MovableModel      MovableModel   (one clone each)
 coords           coords           coords            coords
 minus_forces     minus_forces     minus_forces      minus_forces
 ligand tree      ligand tree      ligand tree       ligand tree
 Rng(spawn(1))    Rng(spawn(2))    Rng(spawn(3))     Rng(spawn(N))
   │                │                │                 │
   └────────────────┴────────────────┴─────────────────┘
                    rayon::iter::IntoParallelIterator
                    results merged, deduplicated, sorted, truncated
```

* `parallel_monte_carlo` iterates `0..exhaustiveness` with
  `into_par_iter()`. Each closure invocation calls `make_model(i)`, which is
  `System::fork(&template)`.
* `System::fork` clones the `Arc<Shared>` (a refcount bump) and clones the
  `MovableModel` (the atoms, the coordinates, the gradient buffer and the
  kinematic trees). Everything the search mutates lives inside that clone, so
  two starts can never touch the same memory.
* Randomness is per task and deterministic: the root generator is
  `Rng::new(seed)` and task `i` uses `root.spawn(i + 1)`. The island GA uses
  `root.spawn(0x9E37_79B9 ^ (island + 1))`. Because the per-task stream depends
  only on the seed and the task index, the whole run is reproducible bit for
  bit for a given seed and parameter set.
* The fourth parallel site is affinity-grid construction:
  `AffinityGrid::populate` chunks the flat `[x][y][z][slot]` buffer along the
  first grid axis with `par_chunks_mut` and fills each slab independently.
* Within one task everything is serial: BFGS iterations, line searches and the
  Monte-Carlo loop are latency-bound and branchy, which is exactly the workload
  a CPU wins at. This is also why the search itself is not offloaded to the GPU
  (see below).
* `EnergyModel: Send`, `ScoringFunction: Send + Sync` and the `F: Fn(usize) -> M
  + Sync + Send` bound on the search entry points are what make the
  `into_par_iter` calls type-check: no `unsafe` and no interior mutability are
  needed anywhere.

## Feature flags

| Feature | Crate | Default | Effect |
|---|---|---|---|
| `gpu` | `dock-core` | off (`default = []`) | Enables the optional `wgpu` compute backend for affinity-grid construction. Pulls in `wgpu` 25 (`default-features = false`, with the `wgsl`, `dx12`, `metal` and `vulkan` backends), `bytemuck` 1 (with `derive`) and `pollster` 0.4. |

Details that matter:

* With `gpu` off, `gpu::request_adapter()` returns
  `Err(DockError::Gpu("dock-core was built without the `gpu` feature; rebuild
  with `cargo build --features gpu` to enable the wgpu backend"))`, and
  `gpu::available()` is `false`. `gpu::populate_grid` still exists and simply
  runs the CPU implementation, so callers never need to branch.
* With `gpu` on, `populate_grid` tries the compute shader first and falls back
  to the CPU path whenever there is no adapter, the device is lost, or the
  force field is not grid-capable (AD4), printing a single line to stderr.
  A GPU build is therefore never *required* to produce a correct result.
* The WGSL kernel (`gpu/grid.wgsl`) is a pure gather: one invocation per
  `(x, y, z, atom_type)` sample point with `@workgroup_size(64)`, which walks
  the receptor atoms and accumulates `pair_energy` inside the cutoff. It
  declares a uniform parameter block, the receptor atom array, the output array
  and a force-field parameter block (radii, hydrophobic/donor/acceptor flags,
  term weights, Gaussian offsets/widths and slope-step bounds); the host
  currently creates bind-group entries for the parameter, atom and output
  buffers.
* `dock-py` declares no features of its own. The Python extension is always
  built against `dock-core` with default features, so `odock.gpu_available()`
  reports `False` for a wheel built from this configuration and the CLI always
  builds its grid on the CPU. The `gpu` feature is reachable from Rust, e.g.
  `cargo build -p dock-core --features gpu`. The CPU grid builder and the GPU
  grid builder evaluate the same terms at the same sample points, so the
  integration does not depend on which one ran.

```bash
# Kernel unit tests (Rust).
```

## Design invariants worth knowing

* **Tree, not graph.** A rigid body plus a spanning tree over the rotatable
  bonds spans exactly the same conformation space as the full molecular graph,
  but every conformation is generated in one forward pass with no constraint
  solving. The tree never crosses a ring, so each ring stays rigid — the same
  approximation AutoDock 4 and Vina make.
* **One scoring implementation.** The grid stores `pair_energy_xs` values and
  the exact scorer calls `pair_energy` over the same `Term` objects, so the two
  paths cannot drift apart.
* **Immutable shared state.** `Shared` is only ever mutated before the `Arc` is
  handed to a search; afterwards `rebuild_grid` goes through `Arc::make_mut`,
  which clones if (and only if) another reference exists.
* **Determinism.** Same seed, same parameters, same platform → same pose list,
  because the RNG is implemented in-tree, the perception is deterministic and
  the pose container merge order is fixed by the ordered rayon collection.
* **No `unsafe`.** The kernel is `#![deny(unsafe_code)]`; the only code that
  could justify an exception would be explicitly annotated SIMD intrinsics, of
  which there are currently none.
