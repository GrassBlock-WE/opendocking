# Changelog

All notable changes to OpenDocking are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project
adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## 0.4.4 — 2026-10-18

### Fixed

* **A count was pinned where the invariant belongs.** `test_cross_rescoring_of_a_real_docking_run`
  asserted

  ```python
  assert len(result.poses) == 4          # 2 conformations x num_poses=2
  assert rescoring.shape == (4, 2)
  ```

  which is **this machine's** answer. On the CI ubuntu legs the same call returned **three**
  poses, because `min_rmsd` merged one pair — so the test was asserting Linux's merging
  behaviour rather than the thing it exists for. It now asserts the **coverage**:

  ```python
  assert len(result.poses) >= 2
  assert rescoring.shape == (len(result.poses), 2)
  ```

  Every pose that comes back is rescored in every conformation; if one is dropped from the
  rescoring, the shape stops matching. The count is gone and the teeth are not.

  **A seed guarantees reproducibility, not a count.** This is the same finding as the
  `exhaustiveness=8` single-pose result that produced eleven `ERROR at setup` in 0.4.2: the
  engine's pose count is an engine-and-platform fact, and any assertion that pins it is an
  assertion about one machine.

### Verified

`tests/test_ensemble.py` → **37 passed**. This release changes **one test file and no shipped
source**; the last clean-environment full run is the one reported with 0.4.3
(**2209 passed, 1 skipped, 0 failed**).

### Still open

Three pharmacophore tests assert counts that depend on how many conformers ETKDG produces
(`hits.n_rejected == 4` refuses one more on CI; the ranked top five differs by one member).
They need the same treatment: assert *which*, or assert the ordering property, rather than
*how many*. `n_total == 17` is not one of them — the bundled library is **hand-written and
checked in**, not generated by `make_demo.py`, so the CI legs read the same 17 molecules the
release does (verified in `examples/make_demo.py`).

## 0.4.3 — 2026-10-18

### Fixed

* **`perceive_nucleophiles` probed the receptor *text* with `Path(...).exists()`, which raises
  on POSIX.** The function accepts a path **or the PDBQT text**, and decided which by calling
  `Path(value).exists()`. For the text case that is:

  ```
  OSError: [Errno 36] File name too long:
  'REMARK  OpenDocking receptor preparation\nATOM      1 N    GLY A 672 ...'
  ```

  measured on the CI ubuntu legs, where the test that passes receptor text failed outright
  while passing on Windows — where the probe simply returns `False`. The input is now
  classified **by shape first** (a newline, or a length that cannot be a path, means text),
  and the probe itself can no longer raise: an `OSError` from `exists()` is treated as "this
  is text", which is exactly what `ENAMETOOLONG` means here.

  A test simulates the POSIX probe — a `Path.exists` that raises `OSError(36)` for anything
  longer than a filename — because **no local run reaches that branch**. That is the same
  lesson as `0.4.1`: a test whose failure only happens on a platform you are not using has to
  assert the mechanism, not the outcome.

### The four remaining failures are one premise, not four defects

The CI failures that are left cluster tightly around **counts**, all off by one:

| test | difference |
|---|---|
| `ensemble cross_rescoring` | `3 == 4` (one fewer) |
| `pharmacophore screening_ranks_the_five_actives_first` | order differs (`benzylamidine` vs `aspirin`) |
| `pharmacophore shape_constraint` | `5 == 4` (one more) |
| `pharmacophore enrichment` | `6 == 5` (one more) |

Every one is "one pose or one conformation different", which is the same root as the
`exhaustiveness=8` single-pose finding on Linux, compounded by the CI regenerating `demo/`
with `make_demo.py --fast`. **The next step is to measure how many poses and conformations the
CI legs actually produce**, and then decide whether the assertions or the premise is wrong -
not to adjust four numbers.

### Verified

`tests/test_covalent.py` → **30 passed**; full suite in a clean environment →
**2209 passed, 1 skipped, 0 failed**.

## 0.4.2 — 2026-10-18

### Fixed

* **One hard assertion in a session-scoped fixture was costing eleven `ERROR at setup`.** The
  CI ubuntu legs reported `12 failed, 2069 passed, 11 errors`, and all eleven errors were the
  same line inside `reproducible_project`:

  ```python
  assert len(result.poses) >= 2
  E   AssertionError: assert 1 >= 2
  ```

  How many distinct poses one seed returns is an **engine and platform fact**, not a
  guarantee: on Linux the search converges more tightly and `min_rmsd=0.5` merges the rest, so
  `exhaustiveness=8, seed=42` produced **one** pose where Windows produced several. Because the
  fixture is session-scoped, that single assertion failed once and then every test depending on
  it errored — with a traceback whose last frames point at `pathlib`, which is why it read as a
  systemic environment failure for two rounds.

  A capability the machine does not provide is now a **skip with the measurement in it**,
  naming the count and the parameters. Eleven errors become eleven skips that say exactly why,
  and the assertion still holds on platforms that do produce a spread.

  The general rule this belongs to: **a strong assumption inside a shared fixture is paid for
  once per dependent test.** It is the same shape as a rule implemented in several places and
  corrected in one — one place too strict, the cost distributed across everything downstream.

spread). This release changes **one test file and no shipped source**, so the package is
untouched; the last clean-environment full run is the one reported with 0.4.1

## 0.4.1 — 2026-10-18

### Fixed

* **`0.3.16`'s fix for the foreign-path rule was itself correct only on Windows.** It used
  `path.name`, which splits **only on the running platform's separator**, so on POSIX

  ```python
  Path(r"C:\Users\someone\.venv\Scripts\python.exe").name
      == r"C:\Users\someone\.venv\Scripts\python.exe"      # the whole string
  ```

  — the ubuntu legs therefore returned the raw Windows path unchanged, and the very defect
  being fixed reappeared one line lower. Worse, it **broke a test that had been passing**:
  `test_no_absolute_path_reaches_the_report` builds `C:\Users\someone\.venv` and asserts
  none of it reaches the report, which stopped being true.

  The final component is now split on **both** separators, in a helper that does not consult
  the running platform at all:

  ```python
  def _final_component(raw: str) -> str:
      stripped = raw.rstrip("\\/")
      return re.split(r"[\\/]", stripped)[-1] if stripped else ""
  ```

  Verified with the exact CI inputs: `C:\...\python.exe` → `python.exe`,
  `/opt/venv/bin/python` → `python`, `D:/data/x/y.pdbqt` → `y.pdbqt`.

* **A test now pins the helper on whatever platform is running.** The existing tests asserted
  the *outcome* and therefore passed here, where a Windows path is native and takes the other
  branch entirely. `test_the_foreign_path_tail_is_split_on_both_separators` asserts
  `_final_component` directly with a Windows path, so this class of bug fails locally instead
  of only on the ubuntu legs.

  That is the point worth recording: **a test that only fails on the platform you are not
  using cannot be verified by running the suite.** Either it asserts the helper, or it has to
  be run on that platform.

### Verified

`test_project` + `test_htmlreport` + `test_protocol` → **121 passed**; full suite in a clean
environment → **2208 passed, 1 skipped, 0 failed**.

### Still open

The CI Python legs still fail the same clusters, now with this fix in place: the four
path-portability tests and `test_no_absolute_path_reaches_the_report` should clear; the
remaining are three real-docking tests (`ensemble cross_rescoring`, `screen campaign`,
`service submit_poll_fetch`), three chemistry/statistics tests
(`test_read_sdf_skips_a_broken_record`, `covalent perceive_nucleophiles`,

## 0.4.0 — 2026-10-18

A **minor** release, because the seventeen patch releases since 0.3.0 are not seventeen
fixes with a release number each — they added six workflows, six commands, and a public
programmatic surface. The CLI went from 34 subcommands to **40**; the package from 58 modules
to **64**; the suite from 2058 tests to **2207**.

### New capabilities since 0.3.0

* **`odock covalent`** — covalent docking: warheads, nucleophile perception, reactive
  geometry classified as bonded / near-attack / non-productive, and adducts built and
  relaxed through the project's own minimiser. Its scoring term's continuity is **measured**
  (halving the sample spacing halves the largest step: 2.00 distance, 1.97 angle), and the
  doc states both of its honest edges — a 263-389 kcal/mol strain beside a truncated cysteine
  is a *clash, not chemistry*, and the bundled 1M17 has six cysteines **none of which is
  C797**.
* **`odock standardise`** — the ordered, switchable recipe that decides whether a screening
  result means anything: parse/refuse, repair, desalt, charge, stereochemistry, dedupe
  (canonical *and* tautomer-insensitive), property filters. The deliverable is an **audit**:
  `in == kept + rejected + merged` asserted inside the function, every removed fragment
  named, and a recipe hash in the header.
* **`odock panel`** — profile ligands across receptors, with box sizes reported beside the
  affinities precisely so a "selective" ligand cannot be one that merely had a smaller box
  elsewhere.
* **`odock service`** — a typed, versioned contract (`odock-service`, schema 1) with an
  `http.server` adapter and **no framework dependency**. Security is enforced in the service
  rather than only in the adapter: loopback `Host` check, per-request token, cross-origin and
  `Origin: null` refused, and a non-loopback bind requires an explicit opt-in *and* a token.
* **`odock protocol`** — versioned, validated, diffable protocols with a hash recorded in the
  run, so a third party can ask "was this produced by that protocol?".
* **Cavity classification in the workbench and the export** — `View > Surface > Cavities`
  repaints the surface by class, marks each bottleneck with a sphere at the **measured** neck
  radius, treats a through-tunnel as its own `channel` class, and exports all of it to PyMOL
  and ChimeraX. Measured: 3PTB 9 pockets / 3.28 A, 1M17 12 pockets / 4.48 A.
* **`screen_ligands(config, *, stop=None, on_record=None)`** and
  `_Runner(jobs, stop_event=None)`: a caller-owned cancellation event, so `_Runner.stop()`
  stays the **single** cancellation path. Two workstreams independently needed it.

### The release discipline that came out of these seventeen patches

Most of the patch releases were **not** feature work; they were the cost of the CI matrix
having **never been green** — not on 0.3.0, not on any 0.2.x commit. Fixing that exposed one
recurring shape of defect, recorded here because it has now happened at four addresses:

> **A rule implemented in more than one place, with only one implementation corrected.**
>
> `benchmark.portable_command` checked only the running platform's separator (0.3.3);
> `portable_path` called `resolve()` on a foreign absolute path (0.3.16); the staging command
> and the `.gitignore` engine disagreed about what ships (0.3.13); and the SDF record counter
> was fixed in `standardise.py` and left broken in `chem/ligand.py` (0.3.12, then 0.3.17).
>
> **When a fix does not make the failure go away, the first question is "how many copies of
> this rule are there", not "is the fix wrong".**

Two more rules earned their place in the docs:

* **A library's failure mode is not a semantic judgement.** A junk record returning `None`
  versus a 0-atom molecule; a missing GL context versus a renderer that was never created; a
  parser's record count versus the document's own delimiters. Each was decided by the running
  machine's library version, so each passed where it was written and failed elsewhere.
* **Stage with `odock release stage`, never with a copy command of your own.** The two
  implementations disagreed in both directions inside one week and the gate was right both
  times.

### Verified

Full suite in a clean environment with no `PYTHONIOENCODING`: **2207 passed, 1 skipped,
0 failed**. `cargo test -p dock-core --lib` **116 passed**; `cargo clippy -D warnings` clean.
The CI matrix is still red on its Python legs — that is stated in every release note rather
than hidden, and the remaining failures are named there.

## 0.3.17 — 2026-10-18

### Fixed

* **The SDF record count was still taken from `len(SDMolSupplier)` in `chem/ligand.py`.**
  `0.3.12` changed that in `standardise.py` and stopped there — there were **two record
  counters and only one was fixed**. A document carrying one junk block can make `len()`
  zero on some RDKit builds, and the loop

  ```python
  for index in range(len(supplier)):
  ```

  then never executes: nothing is read, no note is recorded, no warning is emitted. That is
  exactly how `test_read_sdf_skips_a_broken_record_with_a_warning` failed on both CI
  platforms with

  ```

  Emitted warnings: [].
  ```

  while passing on the machine it was written on. Both counters now count the `$$$$`
  delimiters, which is what the document says, falling back to `len(supplier)` only when
  the text cannot be read.

  A test forces the disagreeing case — a stubbed supplier whose `__len__` returns 0 while
  indexing still works — because no local RDKit build reaches it.

### Verified

`test_chem_ligand` + `test_standardise` + `test_prepare_cli` → **250 passed**; full suite in a
clean environment → **2207 passed, 1 skipped, 0 failed**.

### The pattern, stated once more

Four releases have now fixed the same *shape* of defect at four different addresses:
`benchmark.portable_command` (0.3.3), `portable_path` (0.3.16), the staging command versus
the `.gitignore` engine (0.3.13), and this record counter (0.3.12 then 0.3.17). Each time a

## 0.3.16 — 2026-10-18

### Fixed

* **`portable_path` resolved a foreign-platform absolute path against this machine's
  working directory, so it was never recognised as foreign.** The function already detected
  a Windows path on POSIX (`^[A-Za-z]:`, `\`) — and then called `path.resolve()`, which on
  POSIX treats `C:\...` as *relative* and **prepends the working directory**. The path then
  looked "inside the checkout", the relative-to-the-checkout rule fired, and:

  ```
  portable_path(r"C:\Users\someone\.venv\Scripts\python.exe")
      -> 'C:/Users/someone/.venv/Scripts/python.exe'      # expected 'python.exe'
  ```

  Redaction was worse still: `C:\Users\someone\project\.venv\Scripts\python.exe` came
  back as **`C:python.exe`** — the drive letter survived and the path was eaten.

  A path that is absolute for *another* platform cannot be resolved here at all, so it now
  goes straight to the last rule (keep the file name). Verified with the exact inputs the CI
  ubuntu legs used: `C:\...\python.exe` → `python.exe`, `/opt/venv/bin/python` → `python`,
  and `redact_paths` on a Windows-style command leaves **no** absolute path behind.

  This is the same principle as `0.3.3`'s `benchmark.portable_command` fix: **handle
  cross-platform data from the data's point of view, not this machine's.** It was found only
  after `out/ci_logs.py` was repaired — the failure list being quoted before that was a
  **stale log from 0.3.9**, and these four tests had never appeared in it.

### Verified

`test_project` + `test_protocol` + `test_benchmark` + `test_docs` → **122 passed**; full suite
in a clean environment → **2206 passed, 1 skipped, 0 failed**.

### Still open

The real CI failure set is **14 tests** across two platforms, not the three that had been
reported from the stale log. With this release four of them (the path-portability cluster)
should be gone; the remaining clusters are three real-docking tests
(`ensemble cross_rescoring`, `screen campaign`, `service submit_poll_fetch`) and three
chemistry/statistics tests (`test_read_sdf_skips_a_broken_record`,
`covalent perceive_nucleophiles`, `standardise clean_library`).

## 0.3.13 — 2026-10-18

### Fixed

* **The staging gate now names the scratch families this toolchain creates.** `.gh-tmp` was
  removed by hand before 0.3.12's staging but was **not** in the copy command's exclude
  list, so `.gh-tmp/GitHub CLI/device-id` reached the staged tree. What caught it was a
  path-diff against the published tree — **not** `release content`, which checks named
  fixtures rather than "what is here that was not here before".

  `GENERATED_ROOT_PREFIXES` now carries `.gh-tmp`, `.rust-tmp` and `.pytest_cache` with
  their reasons, so `odock release stage` refuses a tree that carries them:

  ```
  odock release stage: 1 generated entry in the release root: .gh-tmp — github CLI's cache
  and device id (its default cache directory is unwritable here)
  ```

  and the message ends with the control the release needs: *"anything here you do not
  recognise is a leak: fix the tree, re-stage, and read this list again."*

* **The real defect was procedural, and it is mine.** The staging path used a hand-written
  copy command with its own exclude list, which is why a directory could be in the cleanup
  list and not in the exclude list. `odock release stage` already existed, already refused
  stray families, and already printed the staged set grouped by top-level entry — running
  it is now the procedure, and the gh/rust caches live **outside** the repository so the
  gate can pass without being told to ignore them.

### Verified

The detector names all ten families and leaves real directories alone; a tree carrying
`.gh-tmp` is refused with the family named; the same tree with the caches outside the
repository stages cleanly (`exit 0`). `tests/test_release.py` → **93 passed**.

## 0.3.12 — 2026-10-18

### Fixed

* **The SDF audit counted records the way RDKit counts them, so a malformed record vanished.**
  `standardise()` enumerated `for index in range(len(supplier))`, and `len()` on an
  `SDMolSupplier` is *RDKit's* opinion of how many records the document holds. A malformed
  block makes that fewer than the document actually contains — measured on the CI legs,
  where `test_an_unreadable_sdf_record_is_an_invalid_audit_entry` saw `n_in` of **1** for a
  two-record file, so the broken record produced **no audit row at all** and the invariant
  `in == kept + rejected + merged` stayed true while a record silently disappeared. That is
  precisely what the audit exists to prevent.

  The count now comes from the **`$$$$` delimiters**, which is what the document says, and
  a record RDKit cannot read becomes an `invalid` audit row at its own position. Verified:
  a two-record file with one malformed block reports `n_in=2, n_kept=1, n_rejected=1,
  balanced=True` with audits `[(1, kept), (2, invalid)]`.

  This is the third defect in this series with the same shape — **a library's failure mode
  used as a semantic judgement**: a junk record coming back as `None` versus a 0-atom
  molecule (0.3.11), a missing GL context versus a renderer that was never created (0.3.9),
  and now a record count that the parser is allowed to disagree with the file about.

### Verified

`test_standardise` + `test_chem_ligand` → **166 passed**; the delimiter count and the audit
rows were confirmed on a constructed two-record file.

## 0.3.11 — 2026-10-18

### Fixed

* **"Is this record a molecule?" was decided by RDKit's failure mode, which is a version
  detail.** `test_read_sdf_skips_a_broken_record_with_a_warning` appends junk to a valid SDF
  and expects a `UserWarning` naming the problem. It passed on the machine it was written
  on and failed on **both** CI platforms with

  ```
  Failed: DID NOT WARN. No warnings of type (<class 'UserWarning'>,) were emitted.
  Emitted warnings: [].
  ```

  The reader classified a dropped record by checking whether `SDMolSupplier[index]` returned
  `None`. Junk text can equally come back as a **0-atom molecule**, and on the CI legs it
  did — so the record was appended to the results as if it were a ligand and no note was
  recorded at all. The rule is now structural and version-independent:
  **a record with zero atoms is not a molecule**, and it is reported as a problem like any
  other unparseable record.

  `tests/test_chem_ligand.py` gained a test that forces the 0-atom branch through a stubbed
  supplier, because no local RDKit build reaches it — the branch existed only on machines
  whose RDKit behaved differently, which is exactly why it went unnoticed.

## 0.3.10 — 2026-10-18

### Fixed

* **The last two GL-dependent tests in `test_sequence.py` had no guard at all**, and they
  failed for two *different* reasons — which is why one blanket fix could not cover them:

  * `test_loading_a_ligand_keeps_the_receptor_in_view` reached

### Note on the previous attempt

`0.3.9`'s follow-up work tried to place these guards with a script that matched
`DockingWorkbench(` and inserted after the first `processEvents()`. It over-applied (adding
guards to tests that never touch the renderer, which then *failed* under the stricter
`require_gl`), it under-applied (it removed a guard that was needed), and it left orphaned
comments. The fix was reverted to the published state rather than shipped, and this release
does it by reading each test and putting the guard where *that* test's renderer actually
comes into existence. **A pattern that fits one test is not a pattern that fits the file.**

### Fixed

* **A recorded command kept the other platform's interpreter path.**

## 0.3.2 — 2026-10-17

**The published source tree could not be built, and all eight CI jobs were red.**
That is the headline, and it is the reason this patch exists.

### Fixed

* **The workspace did not resolve.** `crates/dock-py/Cargo.toml` carried
  `dock-core = { version = "0.2.1", path = "../dock-core" }`. A version requirement on
  an *internal* crate means `^0.2.1` — `>=0.2.1, <0.3.0` — so the moment the workspace
  version crossed 0.3.0, `cargo metadata` rejected the whole thing:

  ```
  error: failed to select a version for the requirement `dock-core = "^0.2.1"`
  candidate versions found which didn't match: 0.3.1
  ```

  Everything downstream failed with it: `maturin develop`, `pip install` from the
  sdist, and **all eight CI jobs** (Rust and Python 3.9/3.10/3.12 across ubuntu and
  windows, plus Wheels and Benchmark) on **both the 0.3.0 and 0.3.1 commits**. The
  local Python suite stayed green throughout, because it runs against a *pre-built*
  extension — which is exactly why no release gate saw it. The dependency is now
  path-only (`dock-core` is never published to a registry, so the path *is* the
  requirement), and a **`cargo metadata` gate** runs in 30 ms before the expensive
  ones, because a release that cannot be built from its own sources is not a release.

* **The output boundary was wrong for every command on a non-UTF-8 console.** `odock`
  prints `Å`, `→`, `—`; on a Chinese Windows the console codepage is GBK and a
  *redirected* stdout is a pipe, so Python encoded with GBK. `Å` (U+00C5) is not in
  GBK, so the command raised `UnicodeEncodeError` — and a parent capturing with
  `encoding="utf-8"` saw **`returncode == 0` and `stdout is None` simultaneously**,
  because failing to decode leaves the attribute unset. That is how the documentation
  test failed for weeks while the same command "worked" by hand. Four modules with
  their own `__main__` block (`tutorial`, `benchmark`, `panel`, `standardise`) bypassed
  `cli._use_utf8_streams()` and now route through it, as do the two release-gate
  scripts `inspect_dist.py` and `check_test_order.py` — a gate that dies of its own
  redirected report fails for a plumbing reason, which is the worst kind. Pinned by
  `tests/test_output_encoding.py`, which forces `PYTHONIOENCODING=gbk` on the child:
  neither CI (a UTF-8 Linux runner) nor a developer shell (usually already set) can see
  this class, so the test has to create it.

* **The documentation gate read chemistry as markup.** A stereo SMILES written as
  `` `C[C@H](F)Cl` `` contains `[C@H](F)`, which the link checker matched as a link to a
  file named `F`, so `docs/STANDARDISE.md` reported **two dead links that are not
  links**. Fenced blocks and inline code spans are now stripped before scanning. The
  check stayed sharp rather than being loosened: it still catches a real dead link and
  still checks **117** local links.

* **The release gate's quick mode could not see a red slow test.** `release check
  --quick` runs `pytest -m "not slow"`, which **deselects** rather than skips — so a
  failing slow test appeared in neither the pass/fail line nor the skip count, which is
  how 0.3.0 shipped six failing tests. `deselected` is now parsed, a quick run declares
  how many tests it never executed, and the full run enforces `EXPECTED_SKIPS` (failing

  suite that never ran finishes fast.

* **`odock tutorial` and `odock docs check` crashed** with `PermissionError:

  verify the tree is gone) used by `tutorial`, `docs`, `release` and `screen`.

  a test reverses `coords` and `ligand_atom_order` together and requires identical

* **The unexplained 0.571 A `top_pose_rmsd` was not non-determinism.** On a re-run
  with bit-identical affinities the archive's `ligand_atom_order` differed from the
  fresh dock's (`C7 C6 C5 C4...` against `C7 C6 C8 C5...`) and the coordinate arrays
  were compared index-by-index; a symmetry-aware RMSD cannot undo an arbitrary
  permutation. After name alignment it is **5.1e-4 A** - the PDBQT's own three-decimal
  quantisation - and the default `--rmsd-tolerance` now inherits that precision,
  because a zero tolerance against a quantised archive cannot be satisfied.
* **`project save --poses` was silently ignored** when `--dock-json` was also given,
  so the archive was built from a source that stores no coordinates - and a PDBQT
  `REMARK VINA RESULT` is *rendered* text at three decimals. The exact JSON values
  now win: `max_affinity_delta` **4.37e-4 to 0.0**.
* **`pdbqt.write_ligand_pdbqt(return_order=True)` reported serial order, not file
  order.** A `BRANCH` record names its parent, so a serial is assigned before that
  atom's line is written; for a thioether the seventh atom in the file is `S` (RDKit
  index 4) while the reported order said `3` (`O C N H C C S H` against
  `O C N C C C S`). The documented `ligand_strain` recipe then raised *"atom order
  does not match the pose PDBQT"* on an ordinary ligand. The writer now records each
  index as it writes the atom, so the order is true **by construction**.
* **`sasa.burial` can no longer be misused the way it was.** `reference_total` for
  `reference="free"` is the **sum of each residue measured in isolation** (224
  residues, **58 377.1 A^2** against an intact receptor's **9 274.9 A^2**, a factor of
  **6.29**), so subtracting it produced a **-357 kcal/mol** nonpolar term. The name
  invited that, so `buried_area` and `buried_fraction` now return **`None`** for that
  reference - a caller gets a `TypeError` instead - `interface_area`'s docstring
  answers "how much area did the partner bury" outright, and it agrees with
  `burial(reference="unbound")` to 1e-12.
* **A document and its test agreed with each other and neither with the run.** The
  overlay docstring said the shape-only ranking puts *one* amidine in the top three
  and the assertion tested for exactly one; the measured count is **two** (against
  three with the electrostatic term). Both now come from the run, and the assertion
  pins the **pair** so a drift says which side moved.
* **Cavity bottleneck spheres were drawn but invisible** inside the opaque surface
  (4 markers, 0 pixels) - now drawn without the depth test, with the state restored
  in a `finally`. The **neck residue list was unbounded**: a 1.3 A neck reported
  **70 residues** straight into an exported selection, now within `neck + 3 A` and
  capped at 12 (measured 5-12).
* The notebook's expected reproduction line still read `tolerance 0 kcal/mol, 0 A`;
  it is now `0.001 A`, the archive precision.

## 0.3.0 — 2026-10-01

The largest step since the first release: five new workflows, a documentation
site, a release tool, and a long list of defects found by measuring rather than
by reading. 1398 -> 1930+ tests.

### Added — new workflows

* **Ensembles.** Dock against several receptor conformations, cluster poses
  across them, and score per-ligand *robustness* — which separates ligands the
  affinity ranking cannot (caffeine 0.814 vs benzamidine 0.004). Cryptic and
  transient pockets are classified across the ensemble with **closure /
  narrowed / detector-disagreement** verdicts, and the detector's own noise
  floor is reported beside every claim: three cavities close when the agonist
  binds (410->4, 352->22, 366->4 A^3, each 5.4-5.7x the local resolution) while
  the trypsin control yields **zero**.
* **One structure, many conformations.** Side-chain rotamers and an
  elastic-network model generate an ensemble from a single crystal. Measured:
  side-chain sampling moves the affinity **0.419** kcal/mol, *less* than the
  **0.558** kcal/mol between two crystal structures of the same protein.
* **Waters.** Networks, conserved/transient/displaced classification, and the
  offline-verified finding that benzamidine's amidine takes the place of a water
  hydrogen bonded to **ASP189**, the S1 specificity residue.
* **Coupling and pathways.** Cross-correlation from the low modes, with the
  distance baseline that makes a coupling readable, and the truncation finding:
  *a specific strong pair is a statement about the mode count; the overall
  pattern is a statement about the structure.*
* **Residue-level windows on the machinery**: the elastic network's low modes
  have site overlaps of -0.002/-0.010/-0.010 with the real antagonist->agonist
  motion, and a generated backbone ensemble produces **no** cryptic candidates —
  *an ANM of one structure is not a substitute for a second crystal structure
  when the difference is a ligand-driven rigid-body displacement of a helix.*

### Added — ligand side

* Pharmacophore models built from **recurring features with per-feature member
  support**, scored with a documented fit and an envelope constraint.
* Property-matched decoys and an enrichment benchmark with **EF1%, EF5%, AUC and

  explanation (see below).

  interval. Against Vina on 17 ligands it is **not significantly correlated**
  (rho +0.297 [-0.278, +0.857]) while Kendall tau excludes perfect agreement, so
  it is a **disagreement detector, not a better ranking**.

### Added — surfaces and interop

* A real solvent-accessible surface, solvent-excluded surface, property
  colouring (Kyte-Doolittle hydropathy, electrostatic potential with a stated

### Documented negative results

Six corrections in this release changed a number without improving the result,
and they are grouped in `docs/FRAGMENTS.md` because the shape repeats: **a
correct observation of a number, an incorrect expectation about a result.** The
defence, now written into the project's practice, is **to name the quantity a
change is supposed to move before making it**. Three of the six: the ESP term
saturating and moving a fragment from 6.87 to **20.61 A**; the same correction
raising a table's top ligand efficiency from 0.618 to **1.243** while the method
did not improve; and two penalties pinned at maximum for every atom of every
pose, so they cancelled and ordered candidates **identically**.

Two further results are recorded as falsified targets rather than successes: the
fragment placement does not land where the ligand's substructures sit, and the
linker enumerator correctly refuses to span a gap created by that failure. And
`docs/FRAGMENTS.md` §1.2 states the physical reason a pure desolvation term
cannot be an objective at all: **desolvation is a counterweight to the
interaction that burial buys, so maximising it alone means maximising solvent
exposure.**

### Known limitations

* `odock project reproduce` reports INCONCLUSIVE rather than PASS, because the
  archive stores affinities rounded to three decimals while the comparison
  defaults to zero tolerance. It is a **false negative** — it never claims a
  success it cannot verify — and the fix (store the unrounded value) is designed
  and recorded.
* The suite gate does not yet fail when the **skip count shifts**, so a moved
  dataset that turns assertions into skips can look green. The mechanism
  (`EXPECTED_SKIPS` plus a runtime floor) is designed and recorded.
* `odock.fragments` has no CLI entry: its placement is **not trustworthy at 3-6
  heavy atoms** in either regime, and §4 of its page is the case against
  exposing it.

## 0.1.0 — 2026-09-30

The first public release: a complete AutoDock-family docking toolchain built on
a pure-Rust kernel, with a Python API, a command line and a 3-D workbench.

### Kernel (`dock-core`, `dock-py`)

* Rigid-cluster / torsion-tree kinematics with forward kinematics and a
  projected degree-of-freedom gradient.
* Three force fields — AutoDock **Vina** (default), **Vinardo** and **AutoDock
  4.2** — with an analytic first derivative for every term, each verified
  against central finite differences.
* Trilinearly interpolated affinity grids with an analytic gradient and an
  out-of-box penalty; every reported pose is refined on the exact pairwise
  surface.
* Three searches: Metropolis Monte-Carlo iterated local search, the island-model
  Lamarckian GA, and the LGA with a **Solis-Wets** adaptive local search.
* `rayon` data parallelism, deterministic seeding, and pause / resume / abort
  (`Docking.pause`, `resume`, `cancel`, `is_running`).
* Batch docking of independent ligands from released-GIL threads
  (`_odock.dock_batch`).
* Optional **wgpu** compute backend (`--features gpu`) for grid construction,
  batch forward kinematics and batch atom-pair evaluation, numerically equal to
  the CPU path.
* PDBQT reader/writer, including the nested `ROOT`/`BRANCH`/`TORSDOF` topology
  language.

### Python layer

* Receptor preparation: HETATM classification and cleaning, structural-water
  retention by distance, co-crystallised-ligand extraction, cofactor and ion
  policies, missing-atom detection, pH-aware protonation (HID/HIE/HIP),
  polar-hydrogen-only conversion, Gasteiger/Kollman charges, AD4 typing, and
  flexible-residue PDBQT export.
* Ligand preparation: `.smi`/`.sdf`/`.mol`/`.mol2`/`.pdb`/`.pdbqt` input in
  batches, ETKDGv3 embedding, MMFF94/MMFF94s/UFF minimisation,
  rotatable-bond perception with an interactive bond locker, and the torsion
  tree writer.
* Library pre-filters: Lipinski, Veber and PAINS.
* Blind pocket detection with volume, buriedness and residue labelling.
* Analysis: symmetry-aware RMSD, RMSD clustering, the six non-covalent

* Exporters: AutoGrid **GPF**, AutoDock 4 **DPF**, Vina **config**, and cleaned

### Known limitations

Recorded in full in [`docs/VALIDATION.md`](docs/VALIDATION.md#7-what-is-not-validated).
In short: the search is rigid-receptor (a flexible-residue PDBQT can be written,
but the kernel's receptor reader folds it back to rigid and says so); the
Kollman charge model is the united-atom scheme, not the AMBER residue tables;
GPU acceleration covers grid construction and batch kernels only; SSAO is a
screen-space approximation; and macrocycle closure sampling is not specially
optimised.
