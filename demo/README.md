# What is in `demo/`, and what the other docking tasks are doing in this repository

This directory is **validation and benchmark data, not duplicate copies of the same
thing**.  Each dataset exists because a different test, benchmark or validation run
consumes it, and several are deliberately redundant so that one part of the repository
does not depend on another being present.  The two docking runs are regenerated by one
command; everything else is committed so a clone can run the suite offline.

```
demo/
  README.md                     this file
  systems/3ptb/                 inputs + the output of one re-docking run (trypsin)
  systems/1m17/                 inputs + the output of one re-docking run (EGFR kinase)
  libraries/library.smi         the 17-molecule screening library
  libraries/actives.smi         the five-target active set for the LBVS benchmark
  libraries/decoys.smi          the 125-molecule decoy pool
  libraries/ligand_from_smiles.{smi,pdbqt}   the SMILES -> PDBQT round-trip fixture
  figures/workbench_preview*.png             the workbench screenshots
```

Everything under `systems/*` is a **docking run**, split the way a run is:

| | inputs | outputs |
|---|---|---|
| `systems/3ptb/` | `receptor.pdbqt`, `ligand.pdbqt`, `box.json`, `config.txt` | `poses.pdbqt`, `result.pdbqt`, `result.json` |
| `systems/1m17/` | `receptor.pdbqt`, `ligand.pdbqt`, `box.json` | `poses.pdbqt`, `result.json` |

`result.json` is the machine-readable record of the run (`name`, `ligand`, `poses`,
`best_affinity`, `best_rmsd`, `crystal_affinity`, `grid_points`, `receptor_atoms`,
`passed`); `poses.pdbqt` is the pose set and `result.pdbqt` the merged best pose.
`vina.exe` lives inside `systems/3ptb/` because that run used the bundled engine; it is
gitignored, so a fresh clone has the data but not the binary.

## The two docking systems

**`systems/3ptb/` — trypsin with benzamidine.  The acceptance system.**
PDB entry **3PTB** (bovine β-trypsin), co-crystallised ligand **BEN** (benzamidine).
It is the system the project's accuracy claims are anchored on: benzamidine is the
published 3PTB ligand, so re-docking it measures whether the pipeline reproduces a known
pose rather than whether it can invent one.  `result.json` records
`best_rmsd`/`best_affinity`/`crystal_affinity`, and `tests/test_docking.py` asserts them.
It is also what the GUI loads for the viewport and interaction tests.

**`systems/1m17/` — EGFR kinase with erlotinib.**  PDB entry **1M17**, co-crystallised
ligand **AQ4** (erlotinib).  It is the second, chemically unrelated system: a kinase
rather than a serine protease, a 29-heavy-atom drug rather than a 9-atom fragment, and a
different box shape.  Two consumers:

* the Rust integration test, which docks it through the crate
  (`crates/dock-core/tests/data/egfr.pdbqt`) — **that fixture is a deliberate copy**: the
  crate's tests must run without the Python tree, so the same receptor is vendored into
  the crate rather than referenced across the boundary;
* the EGFR system of `odock benchmark`, which is why the directory is named by its PDB
  code (`1m17`) and not by its target: the benchmark, the crate fixture and this
  directory then name the same entry.

Reproduce both runs (this is the command that produced `systems/*`):

```bash
python examples/make_demo.py --fast          # both systems, offline, a few seconds
python examples/make_demo.py                 # the same, with the full Monte-Carlo runs
make demo                                    # == the command above
```

and one run by hand, from the repository root (the `config.txt` holds the box and the
file names):

```bash
odock dock -r demo/systems/3ptb/receptor.pdbqt \
           -l demo/systems/3ptb/ligand.pdbqt \
           -c demo/systems/3ptb/config.txt \
           -o demo/systems/3ptb/result.pdbqt --json-out demo/systems/3ptb/result.json
```

## The structures under `tests/data/` — what they are for

These are **not** demo inputs.  They are the validation sets the benchmark and the
ensemble work run on, and they are worth their size because each one carries a result:

| file | PDB entry | ligand | what it is for |
|---|---|---|---|
| `tests/data/3PTB.pdb` | 3PTB | BEN | the acceptance system, in entry form |
| `tests/data/2PTN.pdb` | 2PTN | — (apo) | trypsin without a ligand: **the negative control** for the ensemble work |
| `tests/data/1STP.pdb` | 1STP | BTN (biotin) | the five-system benchmark |
| `tests/data/3ERT.pdb` | 3ERT | OHT (4-hydroxytamoxifen) | the five-system benchmark **and** the ERα pair for the ensemble work |
| `tests/data/1HVR.pdb` | 1HVR | XK2 (XK263) | the five-system benchmark; the HIV-1 protease pair for the ensemble work |
| `tests/data/1ERE_A.pdb` | 1ERE | EST (estradiol) | the ERα crystal pair (with 3ERT) |
| `tests/data/1HXW.pdb` | 1HXW | RIT (ritonavir) | the HIV-1 protease crystal pair (with 1HVR) |
| `tests/data/{BTN,EST,OHT,XK2}.sdf` | — | — | the same ligands as structure files, for the protonation and pocket-field work |

* **`benchmark/baseline.json`** is measured on five systems — 3PTB, 1M17, 1ERE, 1HVR and
  3ERT — which is why those entries appear both here and under `systems/`.
* **The ensemble work** needs *pairs* of crystal structures of the same protein — one
  with the ligand bound and one without, or two with different ligands — so the modelled
  backbone can be compared against something real.  3ERT/1ERE_A (ERα) and 1HVR/1HXW
  (HIV-1 protease) are those pairs, and 3PTB/2PTN (trypsin) is the third: the **negative
  control**, an enzyme whose pocket does not open.
* **The HIV-1 protease pair produced a documented negative result**: the modelled
  ensemble did not find the cavities the crystal pair shows, and that null result is
  reported in `docs/GENERATED_ENSEMBLES.md` rather than quietly dropped.  A negative
  result is why the pair is still here.

## The molecule sets under `libraries/`

| file | molecules | used by |
|---|---|---|
| `library.smi` | 17 | the screening pipeline, `odock screen`/`filter`/`triage`, the pharmacophore fit, and every "a real library" example in the docs |
| `actives.smi` | 11, five targets | the multi-target LBVS benchmark (`odock lbvs`, `docs/LBVS.md`) |
| `decoys.smi` | 125 | the decoy pool `odock decoys` matches against |
| `ligand_from_smiles.{smi,pdbqt}` | 1 | the SMILES → 3-D → PDBQT round-trip fixture |

They are curated **by hand and committed** because a network fetch is not available in CI
and a vendor catalogue would not be redistributable.  `library.smi` is documented
molecule by molecule in its own header (benzamidine is the 3PTB ligand, the analogues
are a congeneric series, and triphenylene and benzoquinone are there so that one molecule
fails each filter), and `decoys.smi` is a pool — not a decoy *set* — from which
`match_decoys` selects.  `docs/LBVS.md` reports the matching quality honestly, including
that this pool cannot match a 387 Da ligand, which is why the enlarged benchmark has one
scorable target rather than five.

## The figures

`figures/workbench_preview*.png` are the screenshots `docs/VISUALIZATION.md` and the
README show.  They are regenerated by the workbench itself, not by the suite; they are
committed because a reader of a rendered README expects them to load.

## Regenerating and verifying

```bash
make demo                    # python examples/make_demo.py --fast --outdir demo
python tools/reorganise_demo.py --verify   # no stale demo/ path anywhere in the tree
```

`make demo` regenerates the two docking runs in place.  The `tests/data/*` structures are
**inputs, not outputs** — committed, never regenerated — and no test writes into this
directory: every test that docks copies what it needs into a temporary directory first.
